# Задание 2. Интеграция с CI/CD и удалённым хранением состояния

## Инфраструктура

Конфигурация Terraform находится в файле [`main.tf`](./main.tf). Для хранения state применяется Yandex Object Storage с S3-совместимым API; имя файла состояния — `test.tfstate`.

> Перед инициализацией Terraform создайте бакет. Учётные данные для backend задаются переменными окружения либо параметрами `-backend-config`.

Конфигурация разворачивает виртуальную машину в Yandex Compute Cloud. К ней подключаются загрузочный и дополнительный диски; в качестве образа используется Ubuntu 22.04 LTS. Доступ по SSH настраивается публичным ключом из переменной `ssh_key`.

Передайте следующие значения через `.tfvars` или аргументы `-var`:

| Переменная | Назначение |
| --- | --- |
| `vm_name` | Имя виртуальной машины |
| `cores` | Число вычислительных ядер |
| `memory` | Объём оперативной памяти в ГБ |
| `disk_size_gb` | Размер дополнительного диска |
| `zone` | Зона доступности; по умолчанию `ru-central1-a` |
| `subnet_id` | ID уже созданной подсети |
| `ssh_key` | Публичный SSH-ключ |

## Секреты GitHub Actions

Добавьте в настройки репозитория секреты, которые использует workflow:

| Имя секрета | Для чего нужен |
| --- | --- |
| `YC_TOKEN` | OAuth- или IAM-токен для работы с Yandex Cloud |
| `YC_CLOUD_ID` | Идентификатор облака |
| `YC_FOLDER_ID` | Идентификатор каталога для создаваемых ресурсов |
| `YC_ACCESS_KEY` | Static Access Key сервисного аккаунта с доступом к бакету |
| `YC_SECRET_KEY` | Секретная часть пары ключей доступа |
| `SSH_PUBLIC_KEY` | Содержимое публичного ключа, например `id_ed25519.pub` |
| `SUBNET_ID` | Идентификатор существующей подсети в нужном каталоге |

Ключи backend передаются Terraform через `-backend-config`, а не записываются в исходные файлы.

## Работа CI/CD

Workflow включает два задания: `plan` формирует план изменений, а `apply` применяет его после слияния Pull Request.

### `plan`

Запускается для Pull Request, направленного в ветку `main`.

Последовательность действий:

1. Получить исходный код и установить Terraform версии `1.16.5`.
2. Выполнить `terraform init`, передав данные доступа к backend.
3. Запустить `terraform validate`, чтобы проверить конфигурацию.
4. Сформировать план командой `terraform plan`, указав необходимые переменные, включая SSH-ключ и имя ВМ.
5. Сохранить план в `tfplan` и опубликовать его как артефакт workflow.

### `apply`

Выполняется при отправке изменений в `main` после слияния Pull Request и только после успешного `plan`.

Задание повторно получает код, устанавливает Terraform и инициализирует backend, затем загружает артефакт `tfplan`. Команда `terraform apply` применяет сохранённый план, то есть использует результат планирования из предыдущего задания.

## Запуск на локальном компьютере

Для проверки конфигурации без GitHub Actions выполните команды из корня репозитория:

```bash
cd Task2Advanced
export $(cat .env | xargs)

terraform init \
  -backend-config="access_key=$YC_ACCESS_KEY" \
  -backend-config="secret_key=$YC_SECRET_KEY"

terraform plan \
  -var="ssh_key=$(cat ~/.ssh/id_ed25519.pub)" \
  -var="vm_name=test-vm" \
  -var="cores=2" \
  -var="memory=4" \
  -var="disk_size_gb=15" \
  -var="zone=ru-central1-a" \
  -var="subnet_id=$SUBNET_ID" \
  -out=tfplan

terraform apply -auto-approve tfplan
```

## Подготовка бакета

При первом запуске создайте S3-бакет вручную — например, в консоли Yandex Cloud или с помощью CLI. Чтобы несколько запусков не обращались к state одновременно, дополнительно рекомендуется настроить таблицу блокировок в YDB.

После настройки удалённого хранения и GitHub Secrets workflow сможет проверять изменения в Pull Request и применять их после слияния. При необходимости конфигурацию можно расширить отдельными окружениями (`dev`, `stage`, `prod`), файлами состояния и наборами переменных для каждого из них.
