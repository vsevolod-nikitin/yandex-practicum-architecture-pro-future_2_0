# Стратегический план развития

План включает три последовательных этапа, рассчитанных на периоды 0–6, 6–18 и 18–36 месяцев, как предусмотрено заданием. Для каждого этапа обозначены основные работы, ответственные роли и ожидаемые результаты.

## Этап 1: Пилотный запуск (0–6 месяцев)

### Цель

Проверить Data Mesh на одном или двух доменах и заложить основу платформы.

| Задачи | Роли | Результат |
| --- | --- | --- |
| Сформировать команду Data Platform Team | Platform Lead, Data Engineer, DevOps | Облачная инфраструктура развёрнута с помощью Terraform как кода. |
| Определить домен для пилота, например «Пациентский поток» или «Финансовые расчёты» | Domain Data Product Owner, Data Engineer | Подготовлен первый дата-продукт. |
| Развернуть Kafka как событийную платформу и Data Lakehouse на базе S3 и Iceberg | Data Engineer, DevOps | Запущен кластер Kafka, настроен Schema Registry и обеспечено подключение к S3. |
| Создать начальный дата-продукт: передавать события из операционной системы и загружать их в Iceberg | Data Engineer (домена), Domain Expert | События публикуются и используются для аналитики. |
| Запустить MVP портала самообслуживания с каталогом DataHub и простым инструментом создания отчётов | Frontend/Backend разработчики | Участники пилотного домена могут самостоятельно формировать базовые отчёты. |
| Подготовить команду пилотного домена к работе с платформой | Тренеры, Platform Team | Команда способна работать с платформой без постоянной поддержки. |
| Бизнес-цель: вдвое сократить время подготовки отчётности по выбранному домену |  |  |

## Этап 2: Расширение и масштабирование (6–18 месяцев)

### Цель

Распространить Data Mesh на важные домены, внедрить федеративное управление и развить потоковую аналитику.

| Задачи | Роли | Результат |
| --- | --- | --- |
| Подключить дополнительные домены: медицинские записи, ИИ-сервисы и инвентаризацию | Data Product Owners новых доменов, Data Engineers | Каждый домен предоставляет собственные дата-продукты. |
| Согласовать общие правила для схем, качества данных и безопасности в рамках федеративного управления | Data Governance Council (представители доменов), Data Stewards | Подготовлены и утверждены Data Contracts. |
| Создать потоковые витрины на Kafka Streams или Flink для аналитики почти в реальном времени | Data Engineers (платформа), Streaming Engineers | Данные в витринах обновляются с задержкой менее одной минуты. |
| Внедрить антикоррупционные слои для связи с устаревшими системами через Camel и DWH | Integration Engineers | Легаси-системы интегрированы через ACL, события поступают в Kafka. |
| Дополнить портал инструментами для сложных отчётов и подписки на события | Frontend/Backend разработчики | Пользователи создают собственные отчёты и получают уведомления по подписке. |
| Организовать обучение для команд новых доменов | Platform Team, Тренеры | Компетенции сотрудников в работе с платформой растут. |
| Бизнес-цель: охватить 80% основных бизнес-процессов и ускорить получение отчётности втрое |  |  |

## Этап 3: Развитая платформа и инновации (18–36 месяцев)

### Цель

Завершить переход с легаси-систем на слабо связанную событийную платформу и создать условия для развития новых направлений бизнеса.

| Задачи | Роли | Результат |
| --- | --- | --- |
| Прекратить эксплуатацию легаси-DWH и шины Camel | Архитекторы, Integration Engineers | Все данные предоставляются через дата-продукты. |
| Открыть внешним партнёрам — фармацевтическим компаниям и производителям — доступ к самообслуживанию через API | Data Product Owners, API Developers | Партнёры получают доступ к данным по защищённым API. |
| Внедрить Data Observability для автоматического контроля качества данных и lineage | Platform Team, Data Stewards | Проблемы с данными обнаруживаются заблаговременно. |
| Развивать ML-платформу, чтобы Data Scientists могли самостоятельно находить и получать данные для моделей | ML Engineers, Data Scientists | Модели используют актуальные данные из Data Lakehouse. |
| Подключать новые географические регионы с учётом местных требований | Domain Teams, Compliance | Развёрнуты локальные экземпляры платформы с соблюдением нормативных требований. |
| Сокращать расходы на облачную инфраструктуру за счёт автомасштабирования и Spot-инстансов | DevOps, FinOps | Совокупная стоимость владения (TCO) уменьшается без ухудшения производительности. |
| Бизнес-цель: выйти на три новых региона, ежегодно запускать пять продуктов и сократить подготовку отчётов до нескольких минут |  |  |

## Основные роли и их ответственность

**Data Product Owner** — бизнес-представитель, который определяет требования к дата-продукту, отвечает за его качество и планирует развитие.

**Data Engineer домена** — создаёт и сопровождает доменные конвейеры обработки данных, а также обеспечивает публикацию событий.

**BI-аналитик** — пользуется порталом, готовит отчёты и помогает формулировать требования к дата-продуктам.

**Platform Data Engineer** — развивает платформенные компоненты (Kafka, Iceberg, DataHub, Trino) и отвечает за их надёжность и возможности самообслуживания.

**Data Governance Lead** — организует федеративное управление данными и координирует разработку стандартов.

**DevOps** — автоматизирует инфраструктуру и CI/CD, настраивает мониторинг.

**Тренеры и Change Managers** — обучают команды и помогают им адаптироваться к изменениям.
